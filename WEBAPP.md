# Deskmates mobile webapp — stack & current state

Snapshot as of 2026-09-11. Covers the new mobile web client only — see
`docs/SETUP.md` for the WebSocket backend (personalities, memory, canned
responses, ops).

## Stack

- **Vue 3** (`^3.5`) with `<script setup>` SFCs, no Vuex/Pinia — app state
  lives in a handful of plain reactive singletons under `src/composables/`.
- **Quasar** (`^2.32`) via `@quasar/vite-plugin` (not the Quasar CLI) —
  components are auto-imported per-usage by the Vite plugin, so there's no
  manual component registration anywhere.
- **Vite** (`^8`) for dev/build. `npm run build` outputs to `webapp/dist`,
  which nginx serves directly — there is no Node process for the webapp
  itself, only for the existing WebSocket backend.
- No router, no state-management library, no CSS framework beyond Quasar's
  own + a small set of hand-rolled `--bb-*` CSS variables in `App.vue` for
  the app's dark theme.

Source lives at `/var/www/deskmates/webapp`, sibling to the backend, and is
gitignored under `webapp/dist/` (build artifact) and `webapp/node_modules/`.

```bash
cd /var/www/deskmates/webapp
npm install       # first time / after a dependency change
npm run build     # -> webapp/dist, picked up immediately by nginx
```

No service restart is needed after a webapp rebuild — nginx serves the
static files directly. The backend (`server.js`) is a separate systemd
service (`deskmates.service`) and only needs restarting for backend code
changes.

## How it's served (nginx)

`/etc/nginx/sites-available/deskmates`'s `location /` does double duty: it's
both the WebSocket endpoint (console *and* this webapp both connect to
`wss://this-host/?token=...`) and the webapp's static root. There was never
a separate "WebSocket-only" location to leave alone — `/` always was the WS
endpoint — so the same location now also has `root webapp/dist;` and
`try_files`, with an `if ($http_upgrade) { proxy_pass ...; }` gate so a real
WS upgrade still reaches the Node backend exactly as before, and everything
else falls through to the SPA's `index.html`. `/console` is untouched.

## Protocol / backend contract this app relies on

- Auth: `?token=<BOT_AUTH_TOKEN>` query param on the WS URL, same as
  console. Also connects with `&client=console` — this is required
  server-side to unlock `list_personalities`/`set_personality` (gated to
  `ws.isConsoleClient`, not a separate auth tier). Every audio-bearing
  request from this app sets `raw: true`, so despite `client=console` it
  never receives WAV-wrapped audio server-side (`prepareOutgoingAudio` skips
  WAV-wrapping whenever `raw` is set) — same behavior console's own
  auto-conversation mode already relies on.
- `session_id` query param is sent (a client-generated UUID persisted in
  `localStorage`) and is now used server-side for session continuity:
  `src/sessionMemory.js` keys session memory by `ws.sessionId` (a small
  `Map<sessionId, turns>`) instead of storing it on the raw `ws` object, so
  a reconnect carrying the same `session_id` resumes the prior turns
  instead of starting empty. On close, a session's entry is scheduled for
  removal after a short grace window (long enough to survive the
  auto-reconnect backoff below, short enough not to accumulate forever); a
  reconnect within that window cancels the pending eviction. Connections
  with no `session_id` (the physical bot, console) fall back to the old
  per-connection behavior unchanged.
- `speech_result` now carries `text` (the line Claude generated) and
  `user_text` (the STT transcript) — added in `server.js`/`speechPipeline.js`
  for this app; no other message types or audio framing changed.
- `canned_result` now carries `text` when available, looked up from
  `data/phrase-manifest.json` (`src/cannedResponses.js:lookupCannedText`).
  Only categories generated by `scripts/generate-stock-phrases.js` (the big
  `shared/<category>/` list — Fact, LEDModuleInsert, BatteryLow, etc.) have
  persisted text. `greeting` and `filler` were generated by the separate,
  intentionally non-persisting `scripts/generate-canned-lines.js` and have
  **no text anywhere** — those correctly omit `text`, and the UI shows "(no
  transcript line for this turn)" rather than treating it as an error.
- Mode is hardcoded client-side to `"friendly"` (`session.js`'s
  `DEFAULT_MODE`) — there's no mode picker in this app. `friendly` vs
  `sentry_intruder` is normally decided by the physical bot's own camera/face
  recognition, which a phone has no equivalent of; `deep_thoughtful` is a
  transient server-side override the protocol never reports back anyway (see
  "Known gaps" below).
- `task_notification` (`{task_id, title, status}`) is pushed, unprompted, to
  every currently-open `client=console` connection whenever a delegated task
  (`src/delegatedTasks.js`) finishes — `src/consoleLink.js`'s broadcast,
  independent of the physical bot's own `task_done` chime (`src/robotLink.js`
  / `sendOrQueueBotFrame`). A connection that's gone by the time the task
  finishes just misses it, same as the bot-queuing path for an offline
  robot; `list_tasks` already covers catching up on demand. This app shows
  it as a one-line `$q.notify` toast (`composables/taskNotifications.js`,
  wired in `App.vue`) — visual only, never spoken.

### Visualizations

Three today (Pulse, Bars, Orbit), swiped between via `QCarousel` in
`VisualizerCarousel.vue`, with dot navigation and the last choice remembered
in `localStorage` (`deskmates_visualizer`). Every visualization is a
prop-only component — `{ state, mode, level, primaryColor, secondaryColor }`
in, nothing else — so adding a fourth is: write the component, add one entry
to `VISUALIZERS` in `visualizerRegistry.js`, done. Tempo (how fast each one
animates) is still hardcoded per-mode inside each visualization; only color
is user-configurable.

### Color drawer

Palette icon in the top toolbar opens a right-side `QDrawer`
(`ColorSettingsDrawer.vue`) with primary/secondary color wheels for all
three known modes (`friendly`, `sentry_intruder`, `deep_thoughtful`) —
`ColorWheel.vue` is a small hand-rolled `<canvas>` hue/saturation wheel plus
a lightness slider and hex input (Quasar's built-in `QColor` doesn't offer a
circular wheel, only a square spectrum, so this isn't reusing a library
component). Choices persist to `localStorage` (`deskmates_mode_colors`) and
are merged over built-in defaults on load, per mode, with a "reset to
default" button per mode.

Only `friendly`'s colors are visible in practice right now — see the mode
gap below.

## Known gaps / deliberate deviations

- **`sentry_intruder` is unreachable (by design).** `speech_result` and
  `text_result` carry `effective_mode`, so the `deep_thoughtful` theme shows
  live and reverts on exit/expiry. Requests always send `friendly`; the
  phone has no camera so it can never enter `sentry_intruder`. The
  `deep_thoughtful` browser check is still to be done on a real device.
- **No VAD threshold UI.** Console exposes a slider; this app hardcodes
  `VAD_THRESHOLD = 0.02` in `useAutoConversation.js` since the mobile UI has
  no equivalent control surface today.

## Testing status

Verified so far: webapp builds clean; `server.js`/`speechPipeline.js`/
`cannedResponses.js` changes syntax-checked and exercised live (manifest
hit/miss for `text`, full STT→LLM→TTS round trip via
`scripts/test-client.js`); nginx config tested (`nginx -t`) and reloaded;
`/console` and `/` both verified serving correct content over the public
HTTPS domain; a real WebSocket handshake through nginx to the Node backend
verified post-routing-change; file permissions checked so the nginx worker
(`www-data`) can read `webapp/dist`.

**Not verified:** anything requiring an actual browser — mic capture, the
VAD loop end-to-end, the visualizer carousel's swipe gesture, the color
wheel's pointer interaction, or the clipboard copy buttons. This dev
environment has no connected browser and no headless browser installed, so
all of that is verified by code review only. Load
`https://your-domain.example.com` on a phone and walk through it
live before calling this done.

## Build queue drawer

The queue icon in the header opens a right-side drawer listing `tasks/pending`
as draggable cards (pointer events, so it works on touch). Dropping a card
POSTs the full order to `/api/queue/order`; the server saves it to
`tasks/queue-order.json` (gitignored) and `run-build-task.js` takes tasks in
that order, falling back to oldest-first for anything not listed. A failed
save reverts the list and shows the error. Logic lives in `src/queueOrder.js`.

## Native phone app: scope note and what shipped instead (2026-09-26)

A build task asked for a native iOS/Android app — persistent conversation
history, voice-first UX, offline caching, push notifications, low latency —
to replace this mobile web app. This repo is the WebSocket/HTTP backend
plus this Vite-built webapp only; an actual native client is a separate
Swift/Kotlin/React-Native codebase with its own build tooling, app-store
signing, and device testing, none of which can be written, run, or verified
from here (the test gate only runs `node:test` against this repo's own
`src/`, plus a webapp build check). Writing one is out of scope for a
single backend/webapp build pass.

What shipped this pass instead closes the gap that's actually reachable
from here — the things a "feels native" chat client needs that a plain
static SPA didn't have:

- **On-demand conversation history, scoped to today.** `src/conversationHistory.js` +
  `GET /api/conversation?session_id=...&limit=...&since=...` reads
  `logs/turns.db` (already durably written per turn by `src/turnLog.js`) and
  returns one session's turns oldest-first, shaped as `{ role:
  "user"|"assistant", text, ts }` bubbles; `since` (an ISO-8601 instant,
  compared lexically against the TEXT `ts` column) restricts this to rows at
  or after that moment. Same `X-Butterbot-Token`/`?token=` auth as every
  other `/api/` route. The Transcript does **not** auto-replay history on
  page load or reconnect — `deskmates_session_id` is a stable id persisted
  in `localStorage` (see below), and turns.db keeps rows for
  `turn_log_retention_days` (default 90), so an unconditional replay on every
  reload used to re-show that client's *entire* retained history each time,
  which only ever grew. Instead, TranscriptPanel's toolbar has an explicit
  "Pull today" button (`composables/session.js`'s `pullTodayHistory`) that
  clears the Transcript and refetches with `since` set to local midnight,
  paired back into `{ user_text, bot_text }` exchanges via
  `conversationHistoryHydration.js`'s `pairTurnsForHydration` so they render
  identically to a live turn. A plain refresh starts from a blank
  scrollback; "Pull today" is how you get today's conversation back.
- **Installable, offline-capable PWA.** `webapp/index.html` links a web app
  manifest (`webapp/public/manifest.webmanifest`) and adds the
  `apple-mobile-web-app-*`/`theme-color` meta tags iOS and Android use to
  render "Add to Home Screen" as a standalone, chrome-less app rather than
  a bookmarked tab. `webapp/public/sw.js` is a small hand-written service
  worker (no build-time PWA plugin — this webapp has no network access to
  install a new dependency from this pass, and one wasn't needed) covering
  exactly two things: a stale-while-revalidate cache for the app shell
  (`/`, `/assets/*`, the icon, the manifest) so the app still launches
  offline, and a network-first-with-cache-fallback strategy for `GET
  /api/conversation` specifically, so the most recently loaded
  conversation stays viewable with no connection. Every other request
  (the WebSocket, every other `/api/` route) passes straight through —
  this is deliberately not a general offline-first cache. Registered from
  `main.js`, feature-checked and best-effort (a browser without service
  worker support just doesn't get it, silently).
- **Voice input/output, chat-app UX, low-latency connection** — already
  served by the same WebSocket protocol this webapp uses (`?token=`,
  `session_id`, `speech_result`/`text_result`, raw PCM audio) — see
  "Protocol / backend contract" above. A future native client reuses this
  as-is; nothing to build backend-side.
- **Push notifications when Gatsby "has something to say"** — still not
  implemented for the general case (a spontaneous message that isn't tied
  to anything the person asked for). One concrete, already-reachable slice
  of this — a delegated task finishing while this app is open — is covered
  by the `task_notification` toast above, reusing the WebSocket connection
  that's already open; it does nothing for a closed tab/app, since that
  needs actual push delivery (Web Push/VAPID at minimum for this webapp,
  APNs/FCM for an eventual native client) plus device/subscription
  registration and storage — a substantially bigger piece of new product
  surface than this pass.

## Audit: are turn/cost/usage figures real? (2026-09-20)

**Already real before this change:** the Turns, Costs and Usage tabs read
`logs/turns.db` (`src/turnLog.js`), which stores the Anthropic response's
`usage` token counts (incl. cache), resolved model/provider, LLM rounds, web
searches, per-stage ms timings, and dollar estimates from the `PRICES` table.

**Was missing:** the live debug console (`public/index.html`) and the webapp
Log view showed no per-turn usage at all.

**Added:** `speech_result` / `text_result` now carry `turn_stats`
(`src/turnStats.js`: tokens, model, est. cost, API-equivalent cost for
subscription turns, TTS character count, stage timings). Both logs print a
`turn stats:` line per turn. Nulls mean "not available", never filler.
ElevenLabs has no dollar price table, so only character count is shown.
